# No CI — the test suite is effectively never run

## Severity: MEDIUM

## Description

`test.py` hard-exits unless the interpreter is exactly Python 3.6:

```python
if sys.version_info[:2] != (3, 6):
    print(
        f"ERROR: These tests require Python 3.6, got {sys.version_info[0]}.{sys.version_info[1]}"
    )
    sys.exit(1)
```

The repository has no CI configuration of any kind, and Python 3.6 is
EOL and absent from typical developer machines.  In practice this
means the test suite is rarely (possibly never) executed, and
regressions — including the total breakage on 3.7+ described in
issue 9 — go undetected.

## Impact

- Changes to `dataclasses.py` land without any automated verification.
- The version pin plus missing CI mutually reinforce: nobody has a
  3.6 handy, so nobody runs the tests, so the pin is never felt.

## Resolution

Added `.github/workflows/tests.yml` with three jobs:

- **test-legacy** — runs `test.py` inside official
  `python:3.6-slim` and `python:3.7-slim` Docker images via
  `docker run` (checkout happens on the host; GitHub-hosted actions
  can no longer execute inside such old containers due to
  node/glibc requirements, so `container:` was avoided).
- **test** — `actions/setup-python` matrix over 3.8, 3.9, 3.10,
  3.11, 3.12 and 3.13.
- **lint** — `ruff check dataclasses.py test.py` and
  `mypy --strict dataclasses.py` on 3.12.

The version pin in `test.py` had already been relaxed to `>= 3.6`
when issue 9 was fixed; no expected-behavior branches were needed —
the suite passes identically on every version.

Verification: 3.8–3.13 were run locally before pushing (217/217 pass
on each).  3.6 and 3.7 have no local interpreter or Docker daemon in
the development environment, so they are verified by the workflow
itself on push.
